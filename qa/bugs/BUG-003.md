## Summary

The founder's primary dashboard shows **"18 Companies."** Production actually has **8 active
companies and 10 archived** ones. The `/companies` page — the authoritative list — shows 8.

The headline KPI overstates the real company count by **125%**.

## Discovery

Found while running a relationship/cascade attack: archiving a company with active descendants
did **not** decrement the dashboard count (18 before, 18 after), which is only possible if
archived companies are being counted.

## Steps to reproduce

1. Note the "Companies" figure on `/dashboard`.
2. Open `/companies` and count the rows (archived are excluded there).
3. Compare. Optionally archive any company and reload `/dashboard` — the number does not move.

## Expected result

The dashboard "Companies" KPI matches the authoritative active-company list, or is explicitly
labelled as including archived entities.

## Actual result

| Source | Value |
|---|---|
| `/dashboard` KPI | **18** |
| `companies` rows, all statuses | 18 |
| `companies` rows, **non-archived** | **8** |
| `companies` rows, archived | 10 |
| `/companies` page listing | 8 |

## Root cause (verified in source)

`web/app/(app)/dashboard/page.tsx:41`

```ts
supabase.from("companies").select("id", { count: "exact" }),   // no status filter
```

Compare `web/lib/data/companies.ts:13`, which powers `/companies`:

```ts
.neq("status", "archived")
```

The dashboard count simply omits the archived filter that the rest of the feature applies.

The surrounding comment (lines 38–40) documents an earlier fix to this same statistic — a
`HEAD`/`Content-Range` issue that made it read 0 — resolved by fetching real id rows. That fix
corrected the *counting mechanism* but did not add the *archived filter*, so the number went
from wrong-low to wrong-high.

**Scope is precise:** the other three dashboard stats are correctly filtered — goals
`.eq("status","active")`, approvals `.eq("status","pending")`, runs windowed to 14 days.
`companies` is the only unfiltered one.

## Blast radius (assessed honestly)

- No data loss, corruption, security or authorization impact. The underlying data is correct.
- Real impact: the founder's at-a-glance view of the business is materially wrong on a headline
  number. Per `CLAUDE.md` §26 — *"incorrect information is itself a production defect"* — and
  §6, numbers shown to the founder must be authoritative.
- **P2 not P1:** it is a read-only display defect with an easy cross-check (`/companies`), no
  false claim of a completed action, and no state divergence.
- Note the ratio is not marginal: **10 of 18 counted companies are archived.** This is not a
  rounding-error discrepancy, and it grows every time anything is archived.

## Related but distinct from BUG-001

Both involve archived companies leaking into active surfaces, but the root causes and fixes are
different, so this is filed separately rather than folded in:

- **BUG-001** — a *join* omits `companies.status`, so child rows cannot show an archived badge.
- **BUG-003** — an *aggregate count* omits a `WHERE` filter.

Fixing one does not fix the other. They do share a theme worth stating to the implementer:
**archived-state filtering is applied inconsistently across the codebase** — correctly in
`getCompanies()`, `getCompaniesForSelection()` and the chat context's `effectivelyActive`
reasoning, but missing in `getDepartments()` and in this dashboard count.

## Likely component

`web/app/(app)/dashboard/page.tsx` line 41.

## Implementation recommendation (NOT implemented by QA)

1. Add `.neq("status", "archived")` to the dashboard companies count, matching `getCompanies()`.
2. Consider a shared helper so "active companies" has exactly one definition
   (`get_effectively_active_companies` already exists as the RPC form) rather than three
   hand-rolled variants that can drift apart.
3. Audit remaining dashboard/report aggregates for the same missing-filter pattern.

## Regression

fixed. Asserts the dashboard's count expression equals the non-archived count.
