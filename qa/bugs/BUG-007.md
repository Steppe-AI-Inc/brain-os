## Summary

Asked about companies, Brain answered:

> "Yes, 3 archived companies: test5, test8, and test9."
> "12 companies (9 active, 3 archived), 16 people, 27 tasks (15 shown), 6 projects…"

**Database truth at that moment: 20 companies — 10 active, 10 archived.**

Brain reported **12**, which is exactly the size of its context window for companies
(`.limit(12)`). It presented the window as the total, and named 3 archived companies when
there are 10.

The archived list it gave (`test5, test8, test9`) omits: `test7`, `test unit`, `test`,
`test3`, `QA-C002-RENAMED-X`, `QA-VERIFY-BU`, `QA-LIFECYCLE-BU`.

## Why this is not the obvious explanation

My first hypothesis — "companies has no count aggregate" — is **wrong**, and worth stating
because it's the natural guess. Line 2013 does issue one:

```ts
supabase.from('companies').select('id', { count: 'exact', head: true }),
```

The real total *is* computed. The defect is one level up.

## Root cause — a Shown/Total asymmetry in the context pack

`supabase/functions/sem-ai-command/index.ts` lines 2037-2047:

```ts
tasksShown:       …, tasksTotal:       …   // ✅ pair
approvalsShown:   …, approvalsTotal:   …   // ✅ pair
companiesTotal:   …                        // ❌ Total only — no companiesShown
peopleTotal:      …                        // ❌ Total only
projectsTotal:    …                        // ❌ Total only
goalsTotal:       …                        // ❌ Total only
salesLeadsShown:  …, salesLeadsTotal:  …   // ✅ pair
inventoryItemsTotal: …                     // ❌ Total only
channelsShown:    …, channelsTotal:    …   // ✅ pair
departmentsShown: …, departmentsTotal: …   // ✅ pair
documentsShown:   …, documentsTotal:   …   // ✅ pair
```

**Five entity types ship a `Total` with no `Shown` counterpart**: companies, people,
projects, goals, inventory.

That matters because the system prompt's truncation rule (line ~594) is written as a
*comparison between the pair*:

> "If `tasksShown` < `tasksTotal` (or `approvalsShown` < `approvalsTotal` …)"

With no `companiesShown`, the model has no field to compare against and therefore no way to
detect that the companies array was truncated. The instruction cannot fire for those five
types.

## The corroborating control, in the same conversation

Tasks — which **do** have the pair — were reported **correctly** in the very same session:

> "27 active tasks total (15 shown here)."

So this is not a model that ignores truncation generally. It honours the rule precisely where
the data supports it, and cannot where it doesn't. That contrast is the strongest evidence
that the gap is structural rather than behavioural.

## Blast radius (assessed honestly)

- No data loss, corruption, or security impact. Reads only.
- The founder asking Brain a counting question about companies, people, projects, goals or
  inventory can receive a number that is silently capped at the window size. Per `CLAUDE.md`
  §26 — *"incorrect information is itself a production defect"* — and §6, which forbids
  presenting truncated data as complete.
- **This is a known recurring class in this codebase.** `qa/KNOWN_FAILURE_MODES.md` records
  the earlier "AI says 20 approvals when DB contains 75" incident. The fix then added the
  Shown/Total pattern — but only for some entities. This is that same class, surviving in the
  five types the original fix didn't cover.
- P2: read-only misinformation with an easy cross-check (`/companies`), no state divergence
  and no false claim of a completed action.

## Implementation recommendation (NOT implemented by QA)

1. Add the missing `…Shown` fields for **companies, people, projects, goals, inventory**, so
   every array in the pack ships as a `Shown`/`Total` pair.
2. Better: make the pack builder emit the pair **structurally** for every collection, so a
   future entity cannot be added with a `Total` and no `Shown`. The asymmetry above is exactly
   what a per-entity hand-written list produces over time.
3. Re-check the system-prompt rule once the pairs exist — it should then fire unmodified.

## Regression

`qa/scenarios-runner/context_pack_shown_total_pairs.md` — asserts every collection in the
context pack ships both `…Shown` and `…Total`, and that a live count question about companies
returns the true total rather than the window size. **EXPECTED_FAIL** until the five missing
`Shown` fields exist.
