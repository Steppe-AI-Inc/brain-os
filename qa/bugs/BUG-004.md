## Summary

`memories` RLS treats **`company_id IS NULL` as an unconditional bypass** — on both read and
write, at **every** sensitivity tier including `confidential`.

Combined with **publicly reachable self-signup**, this means any person on the internet can
obtain an account and **write arbitrary "facts" into the company brain** — and those memories
are retrieved into Brain Chat's AI context, so injected content can later be surfaced to the
founder as institutional memory.

## The chain, each link verified independently

1. **Public signup is live and reachable.** `GET /signup` from a clean unauthenticated browser
   context → **HTTP 200**, no redirect to login. Renders "Create your Brain OS account", a
   full-name field, an email field, "Send verification code", and "Continue with Google".
2. **Signup self-provisions accounts.** `web/app/signup/actions.ts` →
   `signInWithOtp({ email, options: { shouldCreateUser: true, ... } })`. No invitation, no
   allow-list, no domain restriction.
3. **The trigger grants a real role.** `handle_new_auth_user()` inserts
   `role = 'employee', active = true`.
4. **That account can write company memory.** Live-tested via transactional impersonation of a
   zero-membership `employee` profile (the exact shape signup produces):
   `insert into public.memories (company_id => null, …)` **succeeded** →
   `stranger_can_write_unscoped_memory: "true"`, visible memory count went 5 → 6.
5. **Memories feed AI context.** `sem-ai-command` retrieves `memories` into the context pack,
   so injected facts can reach the founder through Brain Chat.

## Root cause (exact policy text, read from production)

```sql
-- memories_select_scope
is_founder_or_admin()
OR (sensitivity='public'       AND (company_id IS NULL OR has_company_access(company_id) OR is_investor_viewer_of(company_id)))
OR (sensitivity='internal'     AND (company_id IS NULL OR has_company_access(company_id)))
OR (sensitivity='confidential' AND (company_id IS NULL OR is_company_manager(company_id) OR is_hr_finance()))

-- memories_write_scope
is_founder_or_admin() OR (company_id IS NULL) OR is_company_manager(company_id)
```

`company_id IS NULL` short-circuits the tier check in **every** branch. A `confidential`
memory with a null `company_id` is readable by any authenticated user, and **any**
authenticated user may insert an unscoped memory.

The intent is presumably "global/company-agnostic memories are shared" — but it was written as
a blanket bypass rather than as an explicitly-authorized global scope.

## What is exposed **today**, stated precisely (not inflated)

Read as a zero-membership stranger: **6 memories**, all `sensitivity = 'internal'`, all
`company_id = NULL`. Four are QA/test fixture noise ("test4 created as a new test company…").
One is a real, mild org-structure fact ("CLIX GPS and Trade-book.ai are operational divisions
of registered companies…").

Confirmed **0** rows currently match `sensitivity='confidential' AND company_id IS NULL`, so
**no confidential data is exposed right now.**

Everything properly scoped stayed locked: approvals, documents, `financial_reports`,
`product_lines`, `sales_leads`, projects all returned **0** for the same account. **The
company-scoped RLS model works** — this defect is specifically the null-scope escape hatch.

## Severity reasoning — P0 considered and rejected

- Not a cross-company leak: company-scoped rows correctly returned 0.
- Not an auth bypass: the user authenticates legitimately.
- Not destruction or data loss.
- Not secret exposure: no credentials/financials reachable.
- **Is** an unauthorized write, which the rubric lists under **P1**.

Placed at the **top of P1** because the write lands in the AI's memory substrate, making it an
integrity/misinformation vector rather than an inert row (`CLAUDE.md` §26: *incorrect
information is itself a production defect*).

**Escalation trigger — re-classify to P0 if either becomes true:**
1. any `confidential` memory is written with `company_id IS NULL` (read exposure becomes real), or
2. Google OAuth signup is confirmed enabled, removing even the mailbox requirement.

## Attacker prerequisites (honest)

Requires completing the email OTP flow, so a working mailbox is needed — but **any** mailbox
qualifies. No invitation, no existing relationship, no company domain. The "Continue with
Google" button suggests an OAuth path that may not require the code at all; **not verified**,
and deliberately not probed further because doing so would create a real auth user in
production.

## Related latent issue (recorded, not separately filed)

`handle_new_auth_user()` ends with
`on conflict (email) do update set auth_user_id = excluded.auth_user_id` — signing up with an
email that already exists in `profiles` **rebinds that profile to the new auth user** rather
than rejecting. Currently **not exploitable**: 0 profiles have an email with a null
`auth_user_id`, and 0 privileged profiles are unbound. It becomes live the moment anyone
pre-seeds a profile row (e.g. onboarding a hire before they sign up). Worth hardening
alongside this fix.

## Implementation recommendation (NOT implemented by QA)

1. **Remove the blanket `company_id IS NULL` bypass** from `memories_select_scope` and
   `memories_write_scope`. If genuinely global memories are wanted, model that explicitly
   (e.g. a `scope = 'global'` column with its own authorization), rather than inferring
   "global" from a null FK.
2. **Restrict who may write memories at all** — writes into the AI's memory substrate should
   require at least company membership, and arguably manager/founder authority.
3. **Decide whether public self-signup should be open.** If Brain OS is a private company OS,
   an allow-list / domain restriction / invitation-only flow is the stronger control. If
   signup stays open, a brand-new account should land in a genuinely inert state.
4. Harden the `ON CONFLICT (email)` profile rebinding noted above.
5. **Audit the same pattern elsewhere:** grep other RLS policies for `company_id IS NULL` used
   as a permissive branch — this is a failure *class*, not a single policy.

## Regression

`qa/scenarios-runner/memories_null_company_scope_not_a_bypass.sql` — **EXPECTED_FAIL** until
fixed. Asserts a zero-membership employee can neither write an unscoped memory nor read
unscoped `confidential` memories.
