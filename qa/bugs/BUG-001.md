## Summary

The `/departments` page lists departments whose parent company has been **archived**, showing
the archived company's name in the "Company" column with **no archived indication of any
kind** — on the same page whose own company picker *correctly excludes* that very company.

The page therefore states two contradictory things about one company, simultaneously.

## Canonical entity IDs (all registered synthetic fixtures)

- Company: `7ba01ff2-6404-4c06-8bc5-4449b50df5de` — `QA-SWARM-TEST-CO-VIA-CHAT`
- Department: `9573a957-eebd-4552-b28a-b8ed2a9de37a` — `QA-SWARM-TEST-DEPT-EDITED`

Both are `REGISTERED`/`ACTIVE` in `qa/FIXTURE_REGISTRY.json`. **No real business entity was
touched.**

## Preconditions

A company exists with at least one department, and the company is archived.

## Steps to reproduce

1. Go to `/companies`.
2. On a company that has a department, open the row menu → **Delete**.
3. Confirm in the dialog (which correctly states the company is *archived, not destroyed*).
4. Go to `/departments`.

## Expected result

Either:
- **(a)** the department is filtered out of the active list, **or**
- **(b)** the row is visibly marked as belonging to an archived company (badge / muted style
  / "archived" label).

Rationale: the same page's company picker already treats archived companies as not-active, so
the table must not contradict it.

## Actual result

The department renders as an ordinary active row:

```
Name                        Company                     Active goals
QA-SWARM-TEST-DEPT-EDITED   QA-SWARM-TEST-CO-VIA-CHAT   0
```

No archived marker anywhere (`/archiv/i` does not match the rendered table). The company
picker on the same page offers only the 8 genuinely-active companies and correctly omits
`QA-SWARM-TEST-CO-VIA-CHAT`.

## Root-cause evidence (code, not speculation)

`web/lib/data/departments.ts` → `getDepartments()`:

```ts
supabase
  .from("departments")
  .select("id, name, slug, company_id, created_at, companies(name)")
  .order("created_at", { ascending: false })
```

- No filter on the parent company's status.
- Selects only `companies(name)` — **never `companies.status`** — so the UI has nothing to
  render an archived badge from even if it wanted to.

Contrast, in the *same* feature, `web/lib/data/companies.ts`:

```ts
export async function getCompaniesForSelection() {
  const { data, error } = await supabase.rpc("get_effectively_active_companies");
}
```

That RPC deliberately excludes archived companies — the file even carries a comment reasoning
about archived *ancestors*. **The intent is established in the codebase; `getDepartments()`
simply does not honor it.** That asymmetry is why this is a defect and not a design choice.

## Blast radius (assessed honestly, not inflated)

- Not data loss, not corruption, not a security or authorization issue.
- The DB stays coherent and restore works correctly.
- Real impact: a user reorganizing the business sees a department attached to a company they
  just archived, with no signal that the parent is archived — so they may believe the archive
  didn't take, or act on a stale org picture. Workaround exists (check `/companies/archived`),
  which is why this is **P2, not P1**.

## FAILURE CLASS — system-wide audit performed (CLAUDE.md §13/§19)

Per the repo constitution, this was treated as a possible systemic class, not a one-off. It
is systemic.

**Static evidence — 24 of 24 data-layer joins are affected:**

```
grep "companies(" web/lib/data/*.ts   →  24 occurrences, ALL of them `companies(name)`
grep "companies(.*status" web/lib/data/*.ts  →  ZERO
```

Not a single data-layer query selects the parent company's status. The only places that
guard archived companies at all are `companies.ts` itself (`.neq("status","archived")` and
the `get_effectively_active_companies` RPC). Affected modules include: `people`, `projects`,
`tasks`, `goals`, `sales`, `proposals`, `products`, `inventory`, `memory`, `approvals`,
`engineering`, `software`, `kpi`, `finance`, `integrations`, `access`, `ai-assistants`,
`factory`, `onboarding`, `departments`.

**Live evidence — confirmed on a SECOND, independent surface (`/people`):**

```
QA-LIFECYCLE-EMPLOYEE    —   QA-LIFECYCLE-BU    —
QA-LIFECYCLE-EMPLOYEE2   —   QA-LIFECYCLE-BU    —
QA-VERIFY-EMPLOYEE       QA Fixture   QA-VERIFY-BU   qa-verify-employee@example.invalid
```

All three are `people.active = true` attached to companies with `status = 'archived'`, shown
with **no archived indication** (`/archiv/i` does not match the page). This is verbatim the
failure pattern the QA charter names as a priority target: *"Business Unit
disappears/archives/deletes BUT employee still appears actively attached to that unit."*

**Production blast radius, measured (not estimated):** 9 archived companies currently have
7 people, 1 task, and 1 goal attached.

**Honest scoping note:** all 7 affected people rows are QA/test residue
(`QA-LIFECYCLE-*`, `QA-VERIFY-*`, `test3/5/7/9` employees), **not real business staff** — so
no real employee record is currently being misrepresented. The defect is nonetheless real and
would behave identically for real staff; the test rows are what make it observable today.

## Likely component

Primary instance: `web/lib/data/departments.ts` → `getDepartments()`, plus the `/departments`
table Company column.

Class: every `web/lib/data/*.ts` query joining `companies(name)` and the corresponding list
components — most notably `people.ts` (already confirmed live).

## Implementation recommendation (for Home PC — NOT implemented by QA)

Prefer **(b) surface the status** over silently filtering, so archived parents stay
discoverable rather than departments vanishing without explanation:

1. Add `companies(name, status)` to the `getDepartments()` select.
2. Render an "Archived" badge / muted treatment when `companies.status === 'archived'`.
3. Consider the same audit for other lists that join to `companies` — this is a *failure
   class*, not a one-off. Sibling surfaces (projects, goals, people) should be checked for
   the same missing parent-status handling before closing.
