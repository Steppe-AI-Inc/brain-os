# Security / tenancy / authority invariants — Factory Node Management + Zero-Touch Auto Enrollment (V1)

- **Part of** the canonical contract `factory-node-management-auto-enrollment.md` (its §3). Single writer: the DIRECTOR capability.
- **The founder text** (`.FOUNDER_TEXT.md`) prevails over this file.
- **"Proved by"** names the acceptance rows (`qa/verification/auto-enrollment-v1/ACCEPTANCE_MATRIX.md`) that fail if the row is
  broken. Each of those AC rows lists this S-row back.
- **Rejection:** a candidate that violates any row is REJECTED.

| # | Invariant (what must be true) | Proved by |
|---|---|---|
| **S-1** | **No authority from hostname, label or resource fitness** (I A.1 §1, I A.4 §7, II.1, II.11). Hostname, node label, physical computer, machine fingerprint and resource telemetry never grant, imply or widen authority or eligibility. Telemetry may only *exclude* (the minimum-resource gate), and a ranking preference may delay assignment to another eligible node by **at most 30 s**. A founder restriction (S-16) only removes eligibility. **Governance test:** can hostname or resource fitness create authority? **NO.** | AC-6, AC-15 |
| **S-2** | **Per-node credentials; no shared secret on an enrolled node** (I A.1 §1, §3; II.4). Each enrolled computer holds its own durable, independently revocable node credential (a key pair; only the public key is stored). The installer never receives a database password, `FACTORY_RUNNER_PG_URL` or any shared credential. No `runner.env` or legacy task exists on an enrolled computer, including a re-enrolled one. | AC-1, AC-4 |
| **S-3** | **Immediate, independent revocation.** Credential status is re-checked **inside the transaction of every node call**, whatever session token the node holds. The call and the revocation are serialized on the credential row (for example, a share lock per call and an exclusive lock at revoke; any mechanism giving the same serialization satisfies the row). So a call either commits before the revocation commits, or is refused: **no effect of a revoked credential commits after its revocation**. After the revocation commits, **every** node call is refused (the S-7 operation list: heartbeat, claim, renew, checkpoint, complete, release, verification claim, certify, register, rotate, report-state, session exchange), including an in-flight completion. Every other node is unaffected, and the revoked node's evidence is intact. | AC-4 |
| **S-4** | **Server-side authority; the node cannot touch its envelope** (I A.1 §3; II.10). Authorization, tenant and node identity come from the authenticated credential, never from request-body fields. **A node credential cannot change its own envelope, role or capabilities.** The envelope is set at Add Computer and amended only by a Factory admin, audited. | AC-1, AC-6 |
| **S-5** | **A release trust root the founder controls, and bytes bound to the certified source** (II.4, II.11). A node executes an artifact only after its manifest signature, key id and digest verify **before execution**, against a **trust set pinned on the node**, never against a key named by the manifest or the API. Refused by name, and never executed: unsigned, tampered (one byte), revoked key, revoked release, correctly signed by a key outside the trust set. Test / dev keys exist **only on disposable planes**; the live plane has no dev channel. **The trust set and the trust mode are fixed in the artifact at build time, per release channel.** Nothing received at runtime adds a key or changes the mode: not an API response, the plane's identity or URL, pairing, the manifest, the environment or a configuration file. The API may deliver revocations only. A production-channel artifact, the only kind a live-plane node installs, has no dev mode: it trusts only the founder's keys (C-3) and refuses a dev-key signature. The live trust set (the founder's public keys) is a **source input**. After C-3 the Director issues a WO-6 revision recording the founder's public keys and key ids, and the implementer's next candidate adds exactly those bytes to the trust-set source (the Director authors no product code). So the release candidate that goes live contains them in its SHA, and it is certified with them. Before C-3 no live-mode release exists. A node pins the trust set embedded in the artifact it installed; it never takes one from the manifest or the API. The release artifact is **built reproducibly from the CERTIFIED candidate SHA by the verifier** (a non-implementer), with every build input pinned: base Node executable by version and sha256, tool versions by lockfile, and no network fetch of an unpinned input. The receipt records the artifact digest and every trust-set entry read back from the built artifact as (key id, sha256 of the public key), with its channel and trust mode. A key id is the key's fingerprint or bound to it one-to-one, and no key id is shared by two keys; after C-3 the production channel's entries equal exactly the keys of the Director's WO-6 revision, with no other key. The dev channel holds only dev keys and exists only on disposable planes. **The digest** (the reproduced digest, the manifest digest, the node's check and the on-machine read at acceptance) is the SHA-256 PE Authenticode image hash, which excludes the checksum field and the certificate table, so the founder's installer Authenticode signature (a founder boundary) never changes it. The digest the founder signs and AC-1 installs at final acceptance is the production-channel artifact's; R-1 rehearses with the dev-channel artifact and its digest, which is recorded separately and never signed by the founder. "Tampered (one byte)" means a byte inside the Authenticode-hashed ranges. The runtime never reads the ranges the digest excludes (the checksum field, the certificate-table entry and the certificate table), and nothing in them affects the trust set, the trust mode, the endpoint or behaviour. The founder signs only a manifest whose source SHA is CERTIFIED and whose digest equals that receipt's reproduced digest. No key the implementer generated or holds is ever a trust root on the live plane. | AC-5 |
| **S-6** | **Pairing security** (I A.3 §2, I A.4 §9). A code is a random public **locator** (unique among live codes) plus a secret of **at least 55 bits of entropy from a CSPRNG** inside the Factory server boundary (I A.1 §3 "random"). It is never derived from a counter or a clock. The secret is verified as `HMAC-SHA256(FACTORY_PAIRING_PEPPER, normalized_code)`, never as a plain SHA-256, and the pepper lives only in the Edge Function secret store (not in any table, vault entry or function source). Limits: **TTL ≤ 15 min**; **≤ 5 failed attempts per locator**, after which that code is revoked; **≤ 20 attempts per source IP per hour** (the connecting peer address as the Edge platform sees it, never a client-supplied header) and **≤ 60 per tenant per hour**, unknown locators included. The code is one-time, atomically consumed, tenant-bound and envelope-bound; every attempt is audited; comparison is constant-time. Revoked, expired and consumed codes fail closed. A pairing code is never a node credential. | AC-8 |
| **S-7** | **An exact route surface.** Session-less: `GET /v1/time` (server time and protocol version only), `POST /v1/enroll/start`, `POST /v1/enroll/complete` and `POST /v1/session` (a key-signed assertion). Node-session operations, exactly: register, heartbeat, claim, renew, checkpoint, complete, release, verification claim, certify, credential rotate, report-state. There is no test-only operation on a deployed API. Everything else is the Admin API, which requires the caller's own Brain OS token. The installer binary is served from public storage (CR-004), not from a Factory route. Any route or operation outside this list is a finding. | AC-7, AC-10 |
| **S-8** | **Factory admin authority, recorded in the Factory** (I A.2; CR-001, CR-003 ratified). An admin action requires both: (a) the live Brain OS role founder / holding_admin, re-derived from the caller's own token on every call, and (b) a row in `factory.tenant_admins` with that caller's auth user id. `tenant_admins` also records the caller's **tier** (`founder` \| `admin`), and only the founder's provisioning step writes it. Founder-only actions (granting `release_broker`; publishing, superseding or revoking a release) require tier `founder` in `tenant_admins` **and** live role founder, so a self-updated `profiles.role` (side finding S1) never reaches them, and a tier-`founder` row whose live role is no longer founder is refused. Supplying the founder's public keys is not an API action: they enter the trust-set source through a Director WO-6 revision (S-5, C-3). Refused: hr_finance, company_manager, team_lead, sales, engineer, technician, employee, contractor, investor_viewer, anonymous, foreign tenant, a self-promoted employee, a holding_admin who self-promoted to founder, and anyone not in `tenant_admins`. UI hiding is never the control. | AC-7 |
| **S-9** | **Tenancy and data boundary** (I A.2). Every factory row carries `tenant_id`, and company-scope match is a hard gate. No product / business data enters the plane. Brain OS production gets no schema change from this feature. | AC-7, AC-10 |
| **S-10** | **Least privilege; one engine; legacy fenced off** (I A.2, I A.4 §5). All authority and lifecycle logic lives in SECURITY DEFINER SQL front doors with a pinned `search_path`. Edge handlers only authenticate and call one front door, with no lifecycle decisions. API roles are least-privilege, read back from the catalog. The production project `pvphxgrtdfrudejjhzjk` and superusers are refused. TLS is verify-full. No DDL from any API. **The legacy shared role `factory_runner` holds no INSERT, UPDATE or DELETE on any authority record:** tenants, `tenant_admins`, computers, credentials, agent principals, pairing, envelopes, policies, release records and release revocations, and the new-model **certification records**, which live in their own table. The legacy verification columns of `agent_runs` keep their `69df2f52` meaning and never count as a new-model certification. Enforcement: the migration revokes the baseline's default-privilege grant for every new table; EXECUTE is revoked from PUBLIC on every front door, each API role holds EXECUTE on its own front doors only, and `factory_runner` holds none; `factory_runner` is granted no role and is granted to no role beyond its `69df2f52` memberships (`pg_auth_members`), and no API role is a member of it; a server guard refuses any legacy write to an authority record. **A server guard also refuses any legacy INSERT, UPDATE or DELETE on a row of a new-model work order, or on a run or checkpoint of an enrolled computer**, including moving a verification-required work order to done; the same holds for an enrolled run's surface lock and for a dependency row that names a new-model work order. For the legacy role the guard leaves such rows unchanged without failing the frozen claim transaction: the `69df2f52` reaper's requeue and expired-lock delete skip them, and the front doors own their expiry. So the authoring set and certification derive only from rows the legacy role cannot write. **No plane-conditioned behaviour.** No SQL object the candidate creates, and no step the founder applies, decides what it does from a value that distinguishes the live plane from a disposable one: `factory.plane_identity`, `current_database()`, `inet_server_addr()` / `inet_server_port()`, a setting, or a row that exists only on live. The production-ref refusal is the one exception. The verifier lists every such reference in the candidate diff, and each is a REJECTED finding. **Every new-model work order requires the reserved capability `factory-enrolled-v1`**, which the frozen legacy claim path cannot hold, and a server guard refuses any legacy write of a reserved capability. So legacy nodes never claim new-model work. **The reverse holds too:** the claim front door refuses a work order without `factory-enrolled-v1`, so a legacy and an enrolled node never hold the same work order, and both fleets hold surface locks in the one `factory.surface_locks` table. | AC-9, AC-10, AC-12 |

| **S-12** | **Secrets never exposed.** The pepper, credentials, private keys, session tokens, pairing codes and signing keys are never logged, printed, committed, placed in a URL or command line, or returned twice. | AC-8, AC-10 |
| **S-13** | **Independence** (I A.3 §1, I A.4 §8; II.1, II.3). A candidate's **authoring set** is every run that held a lease on the work order or wrote a checkpoint the completing run consumed, each with its identity and node. **An identity** is the agent principal bound to the authenticating credential. Each node credential is bound to exactly one Factory-issued agent principal. **Add Computer creates exactly one principal for the computer**, and the enrollment credential is bound to it. A credential issued by rotate (node- or admin-initiated), re-pair or restore is bound to the principal of the credential it replaces. A further principal exists only through the explicit, audited Factory-admin action "create an agent principal", never as a side effect of another action or of any node call; a node can never mint one. A principal so created receives its first credential only through a pairing code a Factory admin issues for it; enrollment binds a credential to the principal its pairing code was issued for (at Add Computer, the computer's first principal), and re-pair targets the principal of the revoked credential. A run records the principal of the credential it authenticated with. A request-body field never counts. Certification requires four things: the certifying run is not in the authoring set; the certifying identity is none of the authoring identities; the certifier holds verifier authority in its current envelope; and the certification names its work order and the exact candidate provenance (the completing run, and the content digest or commit of what it completed). A certification counts only for that work order, and only while that provenance is the work order's current candidate; a new authoring run voids it. **This floor is enforced by the certification front door whatever the policy data says; a policy can only add requirements.** A second run of an authoring identity can never certify. A different hostname, fingerprint or machine is never sufficient on its own. With no eligible verifier, the work stays WAITING and is never self-certified. | AC-3, AC-14 |
| **S-14** | **QA and contract authority** (II.6, II.8, I A.5). The DIRECTOR is the single writer of: the canonical coordination ledgers, acceptance state, binding WOs, acceptance rows, security rows, the verification spec, and the **content** of the independence and campaign policies. Through the Admin API a policy can only be made **stricter**. The S-16 campaign rows cannot be changed by the Admin API during this milestone; changing them takes a Director revision. **One write is permitted:** a Factory admin binds S-16(a) to a computer record at that computer's Add Computer enrollment. The binding is stored on the computer record (audited, admin-set, never node-reported), not in the frozen campaign row. It is add-only: unbinding, and rebinding to another computer, are refused through the Admin API. A mistaken binding is corrected by archiving the wrongly bound computer and enrolling the correct computer again through Add Computer with the binding; no migration writes an S-16(a) binding. The independent verifier contributes immutable, content-addressed receipts. The IMPLEMENTER publishes candidate / fix reports and change requests. It may not alter evidence, self-close, seed a policy beyond the Director rows, or replace a certified suite without a ratified change request. **Governance test:** can the implementer define or alter the contract it is judged against? **NO.** | AC-12 |
| **S-15** | **Isolation** (I A.3 §3). Candidate tests never touch: the live legacy checkout `C:\Users\DELL\dev\brain-os-factory-cp` (frozen at `69df2f52`; no feature or implementation branch is ever checked out there), the live `BrainOS Factory Node` task, `~/.brain-factory/runner.env`, the live plane, production, `master`, or the acceptance machine before acceptance. | **S-16** | **Milestone restrictions** (founder II.1, II.10; I A.3 §1, I A.4 §8; restrictions, never grants). For Auto-Enrollment V1: (a) **no Auto-Enrollment product code is authored on the Home machine by any session or run**, whether Factory-scheduled or not, and the DIRECTOR capability authors no product code; (b) every milestone candidate is **certified on a different physical machine from every member of its authoring set**; at the product layer, a different physical machine means a different enrolled computer record whose machine fingerprint (contract §1) also differs: any fingerprint the certifying computer has reported that equals any fingerprint an authoring-set member's computer reported during the candidate refuses (detection may only restrict), and a hostname or a different fingerprint alone never satisfies it. A signature proves the signing key, not the authoring machine; each receipt records this limitation. For work authored through the Factory, the receipt's authoring set shows no Home-computer run for a work order whose commits change a path outside the Director-document paths. | AC-3, AC-14, AC-15 |
