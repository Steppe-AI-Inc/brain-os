# Security / tenancy / authority invariants — Factory Node Management + Zero-Touch Auto Enrollment (V1)

- **Part of** the canonical contract `factory-node-management-auto-enrollment.md` (its §3). Single writer: the DIRECTOR capability.
- **The founder text** (`.FOUNDER_TEXT.md`) prevails over this file.
- **"Proved by"** names the acceptance rows (`qa/verification/auto-enrollment-v1/ACCEPTANCE_MATRIX.md`) that fail if the row is
  broken. Each of those AC rows lists this S-row back.
- **Rejection:** a candidate that violates any row is REJECTED.

| **S-3** | **Immediate, independent revocation.** Credential status is re-checked **inside the transaction of every node call**, whatever session token the node holds. | **S-5** | **A Factory-managed release trust root that signs only on the founder's authorization, and bytes bound to the certified source** (II.4, II.11, II.18). Test / dev keys exist **only on disposable planes**; the live plane has no dev channel. **The trust set and the trust mode are fixed in the artifact at build time, per release channel.** Nothing received at runtime adds a key or changes the mode: not an API response, the plane's identity or URL, pairing, the manifest, the environment or a configuration file. The founder never generates, stores, copies, fingerprints or uses the release-signing key, and never signs a manifest by hand. A lost or revoked signer key is replaced only after the judged removal step (contract §1), by a new bootstrap, a new trust-set revision, a new candidate and a reinstall on every node. The live trust set (the signer's public key) is a **source input**. After the bootstrap the Director reads the public key from the live plane, read-only, through the signer's public-key function (never from a table), and issues a WO-6 revision recording it and its key id, and the implementer's next candidate adds exactly those bytes to the trust-set source (the Director authors no product code). So the release candidate that goes live contains them in its SHA, and it is certified with them. Before that revision no live-mode release exists. A node pins the trust set embedded in the artifact it installed; it never takes one from the manifest or the API. A node fetches a release only from the release storage address fixed in its artifact at build time, never from an address the plane, a manifest or the environment names, and what it fetches passes the same gate before it runs. The release artifact is **built reproducibly from the CERTIFIED candidate SHA by the verifier** (a non-implementer), with every build input pinned: base Node executable by version and sha256, tool versions by lockfile, and no network fetch of an unpinned input. The receipt records the artifact digest and every trust-set entry read back from the built artifact as (key id, sha256 of the public key), with its channel and trust mode. A key id is the key's fingerprint or bound to it one-to-one, and no key id is shared by two keys; once that revision exists the production channel's entries equal exactly the keys it records, with no other key. The dev channel holds only dev keys and exists only on disposable planes. **The digest** (the reproduced digest, the manifest digest, the node's check and the on-machine read at acceptance) is the SHA-256 PE Authenticode image hash, which excludes the checksum field and the certificate table, so the founder's installer Authenticode signature (a founder boundary) never changes it. The digest the release signer signs on the founder's authorization and AC-1 installs at final acceptance is the production-channel artifact's; R-1 rehearses with the dev-channel artifact and its digest, which is recorded separately and never signed by the release signer. "Tampered (one byte)" means a byte inside the Authenticode-hashed ranges. No key the implementer generated or holds is ever a trust root on the live plane. | AC-5 |
| **S-6** | **Pairing security** (I A.3 §2, I A.4 §9). A code is a random public **locator** (unique among live codes) plus a secret of **at least 55 bits of entropy from a CSPRNG** inside the Factory server boundary (I A.1 §3 "random"). It is never derived from a counter or a clock. The secret is verified as `HMAC-SHA256(FACTORY_PAIRING_PEPPER, normalized_code)`, never as a plain SHA-256, and the pepper lives only in the Edge Function secret store (not in any table, vault entry or function source). Limits: **TTL ≤ 15 min**; **≤ 5 failed attempts per locator**, after which that code is revoked; **≤ 20 attempts per source IP per hour** (the connecting peer address as the Edge platform sees it, never a client-supplied header) and **≤ 60 per tenant per hour**, unknown locators included. The code is one-time, atomically consumed, tenant-bound and envelope-bound; every attempt is audited; comparison is constant-time. Revoked, expired and consumed codes fail closed. A pairing code is never a node credential. | AC-8 |

| **S-13** | **Independence** (I A.3 §1, I A.4 §8; II.1, II.3).
